# 实验设计：同题四体盲排

## 一、要验证的假设

仓库的核心主张是：

> H1：**用了引擎写出来的文章，比让模型直接写更好。**

还有一个隐含主张，从没被检验过：

> H2：**三个引擎是三个不同的东西**，不是同一套话术换三层皮。

H2 比 H1 更脆弱。三个引擎共享同一套方法论（选样→拆解→压缩→实战→反哺），
如果输出读起来分不出区别，那么「文体的操作系统」这个说法就塌了一半——
变成「一个引擎，三种包装」。

所以这个实验同时测 H1 和 H2，并且**先测 H2**：如果三个引擎的输出无法区分，
H1 的胜率就失去了意义（你不知道是哪个引擎赢的）。

## 二、设计：同题四体盲排

```
10 个题目
  × 4 个版本（裸模型 baseline + 3 个引擎）
  = 40 篇
  × 每位评分者评 6–7 题（每题 2 人）
  = 20 次排序判断
```

### 为什么每题只给 2 位评分者

若 3 人都评全部 10 题，每人要读 40 篇（约 3.6 万字），志愿者撑不住，
最后拿到的是敷衍的排序——那比没有数据更糟（它看起来像数据）。

现在每题 2 人、轮流分配：R1 和 R2 各 7 题，R3 6 题，每人 24–28 篇。
由 `blind.py` 生成，写进 `eval/assign.json`，可复现。
代价是单题只有 2 个判断——所以「扩题」比「加评分者」更该优先：
加人能降方差、扩题能同时降方差并提高检验力，而扩题只是多花生成的钱。

### 为什么是「四体排名」而不是「A/B 对照」

A/B 只能回答「引擎 vs 裸模型」，一次只有 1 个自由度。
四体排名一次拿到 3 个自由度：

- 引擎 vs baseline：H1
- 引擎 vs 引擎：H2
- 每题最优是谁：路由数据

代价是评分者每题要比 4 篇而不是 2 篇——这个代价用「每人只评一部分题」来付，
见上一节。

### 为什么每题要给「素材包」

这是本设计最关键的一个决定。

活人感引擎的红线写着：**「无来源案例 = 造假；人物样本必须标注标签+名字」**。
如果只给题目让模型自由发挥，这个引擎只有两条路：①违反自家红线去编 ②拒绝执行。
两条路都让实验失效，而且失效原因跟引擎好坏无关。

所以 `prompts.json` 里每题都塞了一个**统一的素材包**：3–4 个人物样本，
每个 = 标签 + 名字 + 场景 + 一句引语。四个版本拿到完全相同的素材。

这样实验测的就是**同一个工种**：拿到同样的一手材料，
谁能把它组织成更好的文章。而这正是原子技法要解决的问题。

副产品：素材包本身就是一套可复用的测试资产，下次换模型重跑不用重新编。

### baseline 怎么跑

baseline 的 prompt 只有三样：题目 + 素材包 + 字数。**不给任何技法、不给风格说明。**
这是要测的下限。它与引擎版本唯一的差别就是「有没有加载 SKILL.md」。

### 生成规程

对每一题，四次生成必须满足：

| 必须相同 | 必须不同 |
|---|---|
| 模型与版本 | 是否加载引擎 |
| 温度与采样参数 | 加载的是哪个引擎 |
| 题目原文 | |
| 素材包 | |
| 字数要求 | |
| 生成轮次（不用「再试一次挑最好的」） | |

**禁止 cherry-pick**。每版只生成一次。如果引擎版本生成失败/拒答，
记 `FAIL`，按排在最后计分——失败也是结果。

## 三、评分规程

### 交给评分者的东西

只有一个文件夹：

```
t01/A.md  t01/B.md  t01/C.md  t01/D.md
...
t10/A.md  t10/B.md  t10/C.md  t10/D.md
```

标签 A–D 的分配在 `key.json`，每题独立随机，评分者不看这个文件。

### 评分者要做的三件事

每题四篇读完，填一行：

| 字段 | 内容 |
|---|---|
| `rank1`–`rank4` | 从最好到最差的标签顺序 |
| `note` | 一句话：最好那篇里，最像活人写的是哪句 |

`note` 不是装饰。它是唯一能告诉你「原子技法里哪条真的起作用了」的数据——
排序只给结论，这句给人证。

### 评分者怎么选

- ≥ 3 人，彼此不知道对方结果
- 至少 1 人是**目标读者**（会读这类文章的人），不是作者本人
- **作者本人不计入**。自己给自己的引擎排序，等于没测
- 评分者不需要是写作专家。目标读者比专家更接近真实场景

### 一致性要求

算评分者之间的 Spearman 相关系数（`score.py` 自动算）：

- 平均 ρ ≥ 0.5：结论可用
- 0.3 ≤ ρ < 0.5：结论只能看方向，`RESULTS.md` 里要写明
- ρ < 0.3：评分标准不一致，重新对齐标准再评，不要硬发结论

## 四、什么算成功，什么算失败

先定好判据，免得看到数据再回头改标准。

**判据必须看置信区间，不能看点估计。** 这不是洁癖：本仓库第一版 `score.py`
用「胜率 ≥ 60% 就算通过」，结果喂进**完全随机**的排序，它输出了
「H1 通过 60% / H2 通过 75%」。n=20 时 60% 的 95% 区间是 39%–78%，
跟扔硬币分不开。修法是把每条胜率换成 Wilson 区间，判定看**区间是否整体偏离 50%**。

| 指标 | 失败 | 勉强 | 通过 | 强 |
|---|---|---|---|---|
| **H1** 引擎 vs baseline | 区间整体 < 50% | 点估计 > 60% 但区间跨 50% | 区间整体 > 50% | 3/3 引擎区间整体 > 50% |
| **H2** 引擎两两可区分度 | 区间跨 50%（分不出） | 区间不含 50% 但 < 70% | ≥ 70% 且区间不含 50% | 3 对里 2 对 ≥ 70% |
| 评分者一致性 ρ | < 0.3 | 0.3–0.5 | 0.5–0.7 | > 0.7 |
| 每题最优的分散度 | 全被同一引擎拿走 | — | 至少 3 个引擎各拿过 1 题 | 4 类题目各有擅长者 |

`score.py` 会自动算区间并按上表出判读，同时打一条多重比较提醒：
3 次对比较意味着，即使三对完全无差别，也约有 14% 的概率至少一对「看起来可区分」。
所以 H2 只有一对通过时，措辞应是「初步可区分」，不是「三个文体各不相同」。

### 为什么 n=20 不够，以及扩到多少

| 观察到的胜率 | n=20 的 95% 区间 | n=60 的 95% 区间 |
|---|---|---|
| 100%（20/20） | 84%–100% | 94%–100% |
| 75%（15/20） | 53%–89% | 63%–84% |
| 60%（12/20） | **39%–78%** | 47%–72% |
| 50%（10/20） | 30%–70% | 38%–62% |

n=20 只有 100% 和 75% 这种极端结果才显著；连 30%（6/20）都判不了「显著落后」
（区间上界 52%）。这就是第一轮只能给方向性结论的数学原因，
也是「扩到 25–30 题」这个建议的出处。

### 判读规则

- **H1 失败（胜率 < 50%）** → 暂停加引擎。引擎没有价值，先修引擎。
  最大嫌疑是原子技法不可执行（写成了形容词而不是动作）。
- **H1 通过但 H2 失败（三体不可区分）** → 「文体 OS」降级为「一个通用写作引擎」。
  要么合并成一个（诚实做法），要么找出真正的差异点重做区分度。
- **H1、H2 都通过，但每题最优集中在 1 个引擎** → 其余两个引擎是装饰，
  应该下线或重做。**库的价值在深度不在数量。**
- **占比最高的失败模式：baseline 赢在「更短更清楚」。** 引擎容易把文章写长、
  写满、写花。如果 baseline 频繁因「干净利落」获胜，说明原子技法在用密度换质量。

## 五、这个设计测不到什么

诚实列出边界，免得结论被过度使用：

1. **测不到长期写作能力。** 它测的是「一次生成的质量」，不是「教会人写作」。
   课程的效果要另一套设计（前后测 + 学员作品盲评）。
2. **测不到真实素材的获取。** 素材包是我们给的，真实写作里最难的「找到那个人」
   这一环被绕过了。这是刻意的取舍（见 §二），但它意味着结果对「采访型写作」
   的外推要打折。
3. **n=20，样本很小。** 每题 2 位评分者 × 10 题 = 20 次比较。胜率 60% 的 95% 区间
   约 39%–78%。所以 `RESULTS.md` 里只写方向性结论，不写「显著优于」。要更硬的结论，
   扩到 25–30 题（n≈60），成本线性增加。
4. **测不到审美差异。** 三位评分者的共同偏好会掩盖真实读者的多样性。
   如果预算允许，第二轮应该扩到 8–10 位评分者，看分歧本身。

## 六、下一轮要改的地方

跑完第一轮再定。预先说一个方向：如果 H2（可区分度）没过，
下一轮应该改成**「同学科不同题目」**的设计——让每个引擎写它最擅长的那类题，
而不是所有引擎写所有题。因为「三体不可区分」可能不是引擎的问题，
而是题目没有触及各家擅长区。

这个改动会让 H1 的结论变弱（不再是同题公平对照），但会让 H2 变得可回答。
届时两套结果并列报告，不要合并成一个数字。
