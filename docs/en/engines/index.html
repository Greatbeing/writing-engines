Writing engines

A genre is a set of operating rules its authors never state. An engine takes a genre apart to a grain you can execute, then reassembles the parts into something that can write new pieces.

engine = atomic techniques × style fingerprint × red-line review

Atoms govern how a piece is thought up; the fingerprint, how a draft is checked; red lines, what must never appear. Each engine is a self-contained SKILL.md directory with no code dependencies.

How an engine is built

  1. Sample. Choose a genre with clear boundaries and collect real, high-quality texts.
  2. Extract atoms. Take each text apart into its smallest techniques, then merge them into composable operations.
  3. Fix the fingerprint. Turn “sounds like it” into features that can be counted and compared.
  4. Draw red lines. Write down what gives the style away when misused, with a replacement for each.
  5. Feed back from use. Write real pieces with the engine; where they fail, revise the atoms and red lines.

Every engine follows the same seven-section contract (SPEC.md ↗) and must pass the ten checks in lint_skill.py: complete frontmatter, all seven sections, no full-text corpus, and complete sample output.

Install and use

SKILL.md with frontmatter is a common format. With OpenClaw:

git clone https://github.com/Greatbeing/writing-engines.git
# each engine directory is self-contained: copy one, or all
cp -r writing-engines/*-writing ~/.openclaw/workspace/skills/

For Claude Code or any other host that reads SKILL.md, put the engine directory in its skills path. After writing, you can check the result:

# score a piece for AI flavor against one engine
python tools/ai-flavor-checker.py article.md --engine sanlian-writing
# library-wide lint, assertions and regression tests
python tools/lint_skill.py --all
python tools/run_prompts.py --all
